## 設計方針

### 検索APIの設計について

現時点では、`GET /api/v1/friends` エンドポイントを**GET + クエリパラメータ**で実装しています。

**理由**:
- 検索条件がシンプル（キーワード検索、状態フィルタ、広告コードフィルタなど）
- クエリパラメータで十分表現可能
- 画面の詳細が不明な段階では、シンプルな設計から始めるのが適切

**将来的な拡張可能性**:
もし将来的に以下のような複雑な検索が必要になった場合は、**POST + リクエストボディ**への変更を検討してください：

- 複数のOR条件の組み合わせ
- ネストした条件（例：日付範囲 + 複数の状態のOR条件）
- 複雑な日付範囲検索
- 複数のフィールドでのAND/OR検索

この場合、`POST /api/v1/friends/search` のようなエンドポイントを追加するか、既存のエンドポイントを拡張することを検討してください。

## 特に確認してほしい点

### 0. フィールドの対応関係（要確認）

- **質問**: 画面の「管理コード」列が実際に `line_friends.messaging_api_user_id_cms` を表示しているか？
- **背景**: 画面の表示項目とDDLのフィールドを照合した結果、`messaging_api_user_id_cms` が「管理コード」に対応すると推測しましたが、実装を確認する必要があります
- **推奨**: 実際の画面実装や仕様書で確認してください

### 1. 検索機能の実装範囲

- **質問**: `q` パラメータの検索対象フィールドについて
  - 管理コード（`messaging_api_user_id_cms`）、広告コード、LINE ID（`messaging_api_user_id`）の全てで検索可能か？
  - それとも特定のフィールドのみか？
- **推奨**: 全てのフィールドで検索可能にするとユーザビリティが向上しますが、パフォーマンスへの影響を確認してください

### 2. フィルタ条件の組み合わせ

- **質問**: 複数のフィルタ条件（`status`, `advertisement_code`, `line_official_account_id`）を組み合わせた場合、AND条件かOR条件か？
- **推奨**: 一般的にはAND条件が適切ですが、要件に応じて調整してください

### 3. ソート機能の実装可否

- **質問**: `sort` パラメータで指定したフィールド（`created_at`, `id`, `messaging_api_user_id_cms`）でソート可能か？
- **推奨**: インデックスの有無を確認し、パフォーマンスに問題がないか確認してください

### 4. ページネーションのデフォルト値

- **質問**: `limit` のデフォルト値100件で問題ないか？
- **推奨**: 画面の表示件数と整合性を確認してください

### 5. 削除処理の実装方法

- **質問**: 削除処理は論理削除か物理削除か？
- **推奨**: 監査要件を考慮し、論理削除を推奨します
- **質問**: 削除済みリソースの削除リクエスト時の挙動（204 No Contentを返すか、404 Not Foundを返すか）
- **推奨**: 冪等性を保つため、204 No Contentを返すことを推奨します

### 6. 認証・認可

- **質問**: `site_id` の取得方法（認証トークンに含まれるか、別途取得するか）
- **推奨**: マルチテナント対応のため、認証トークンから取得することを推奨します

### 7. レスポンス構造の最適化

- **質問**: `line_connection.line_official_account_name` はJOINで取得するか、別APIで取得するか？
- **推奨**: N+1問題を回避するため、JOINで取得することを推奨しますが、パフォーマンスに問題がある場合は別APIでも可

## バックエンド側で決定してほしい事項

### 1. フィールド名の調整

- API設計では `snake_case` を推奨していますが、バックエンドの命名規則に合わせて調整可能です
- 特に `management_code`, `advertisement_code`, `line_id` などのフィールド名

### 2. データ型の調整

- `id` フィールドは文字列型（`string`）として定義していますが、数値型（`integer`）でも問題ありません
- ただし、将来の拡張性を考慮すると文字列型を推奨します

### 3. 日時形式の調整

- ISO 8601形式を推奨していますが、他の形式でも問題ありません
- ただし、タイムゾーン情報は含めることを推奨します

### 4. 追加フィールドの提案

- 必要に応じて追加フィールドを返しても問題ありません
- 例: `updated_at`, `query_string` など

### 5. ページネーション情報の最適化

- `total_count` の計算が重い場合は、`has_next` や `has_prev` などのブール値で代替することも可能です

### 6. エラーメッセージの調整

- エラーメッセージの文言は、バックエンドの実装に合わせて調整してください
- RFC 9457準拠の形式は維持してください
