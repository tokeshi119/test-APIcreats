# 友だち一覧画面のAPI設計計画

## 対象範囲

- 友だち一覧画面のみを対象とする
- ナビゲーションメニューの他の画面（集計、LINE設定、広告設定、管理者、システム）は対象外

## データベース設計との関係

- バックエンドが作成した仮のDDLを参考情報として参照する
- API設計は画面要件を優先し、DDLは整合性確認用として使用
- DDLのフィールド名や型は参考程度とし、API設計の柔軟性を保つ

### DDLから確認した主要テーブル構造

**line_friends テーブル**（友だち情報）:

- `id` (BIGINT): 主キー
- `site_id` (BIGINT): サイトID
- `advertisement_code_id` (BIGINT): 広告コードID（NULL可）
- `messaging_api_user_id` (TEXT): Messaging API ユーザーID（LINE ID相当）
- `messaging_api_user_id_cms` (TEXT): CMS向けMessaging API ユーザーID（管理コード相当）
- `line_official_account_id` (BIGINT): LINE公式アカウントID
- `is_blocked` (BOOLEAN): ブロック状態（true=ブロック、false=正常）
- `query_string` (TEXT): クエリ文字列
- `created_at` (TIMESTAMP WITH TIME ZONE): 登録日時
- `updated_at` (TIMESTAMP WITH TIME ZONE): 更新日時

**advertisement_codes テーブル**（広告コード情報）:

- `id` (BIGINT): 主キー
- `advertisement_code` (TEXT): 広告コード文字列
- `name` (TEXT): 広告コード名

### 画面表示項目とDDLのマッピング

- **管理ID**: `line_friends.id` または `line_friends.messaging_api_user_id`
- **管理コード**: `line_friends.messaging_api_user_id_cms`
- **広告コード**: `advertisement_codes.advertisement_code` (JOIN)
- **LINE ID**: `line_friends.messaging_api_user_id`
- **友だち登録日時**: `line_friends.created_at`
- **友だち状態**: `line_friends.is_blocked` (true=ブロック、false=正常)
- **LINE連携**: `line_friends.line_official_account_id` と関連情報

## 設計プロセス

### ステップ1: 画面要件の分析

画像から以下を抽出：

- **表示データ項目**: 管理ID、管理コード、広告コード、LINE ID、登録日時、状態、LINE連携情報
- **ユーザー操作**: 検索、ページネーション、削除
- **関連画面**: 現時点では友だち一覧のみを対象

### ステップ2: エンドポイント設計

RESTfulな設計で以下を定義：

- `GET /api/v1/friends` - 友だち一覧取得（ページネーション、検索、フィルタ対応）
- `GET /api/v1/friends/{friendId}` - 友だち詳細取得（必要に応じて）
- `DELETE /api/v1/friends/{friendId}` - 友だち削除

### ステップ3: リクエスト仕様の設計

- **クエリパラメータ**: 検索条件、フィルタ、ソート、ページング
- **パスパラメータ**: 友だちID（管理IDまたはLINE ID）
- 命名規則: パスはkebab-case、クエリパラメータとJSON項目はsnake_case

### ステップ4: レスポンス構造のサンプル提示

- 一覧取得: `total_count`, `page_number`, `items` の構造
- 各友だち情報: 管理ID、管理コード、広告コード、LINE ID、登録日時、状態、LINE連携情報
- エラーレスポンス: RFC 9457準拠の形式

### ステップ5: 共通仕様の定義

- **認証**: Bearer Token（OAuth 2.0）を推奨
- **エラーハンドリング**: RFC 9457準拠
- **HTTPステータスコード**: 200, 201, 204, 400, 401, 403, 404, 409, 422, 500

### ステップ6: OpenAPI形式での文書化

OpenAPI 3.0形式のYAMLファイルを作成：

- エンドポイント定義
- リクエスト/レスポンススキーマ
- 認証方式
- エラーレスポンス

### ステップ7: バックエンドへの引き継ぎ

レビュー依頼文書を作成し、確認事項を整理

## 出力ファイル

1. `api-design/friends-api-spec.yaml` - OpenAPI仕様ファイル
2. `api-design/friends-api-review.md` - バックエンドレビュー依頼文書

## 設計方針

- RESTfulな設計原則に従う
- パスはkebab-case、JSON項目はsnake_case
- ページングはオフセット&リミット方式
- エラーレスポンスはRFC 9457準拠
- 認証はBearer Tokenを推奨（実装時に調整可能）
